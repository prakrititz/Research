## 1. The idea in one picture

Every refinement step produces a **proof obligation**: a logical statement that must be true for the step to be sound. For the paper's square-root loop, one such statement says:

> *If the invariant holds, the guard holds, and the variant equals V0, then after `x := x + e` the invariant still holds and the variant is smaller than V0.*

Three different programs can check that statement:

```
                 the obligation
                       │
        ┌──────────────┼──────────────────┐
        ▼              ▼                  ▼
       Z3             Coq               Lean
  "I searched and   "Here is a proof   "Here is a proof
   found no          script; my tiny    script; my tiny
   counterexample"   kernel checked     kernel checked
                     every step"        every step"
   ~2 ms             ~0.5 s             ~7 s
   huge program      small kernel       small kernel
   (trust it)        (trust only that)  (trust only that)
```

* **Z3 refutes well.** When the statement is false it hands back concrete numbers that break it. That is exactly what a language model needs in order to repair a wrong invariant (see `12`, §6). It is also very fast.
* **Coq and Lean certify.** When the statement is true they produce a proof that a *small* checker (the "kernel") verifies. You do not have to trust the big, clever search that found the proof, only the kernel. This is what the paper's Coq-based pipeline provides. When they **fail** to prove something, that means only "my tactics were not clever enough"; it proves nothing about falsity.

So the design is: **let Z3 do the searching, and let Coq/Lean certify the result.**

## 3. What the obligation looks like in each language `[ran]`

The sqrt loop-body obligation, as generated by the code (`Coq` and `Lean` tabs are the real files that were checked):

**Meaning, in words.** Variables `N, e, x, V0` are real numbers. Assume `N ≥ 0`, `e > 0`, `x² ≤ N`, `x ≥ 0`, `(x+e)² ≤ N`, and `V0 = N − x²`. Show: `N ≥ 0`, `e > 0`, `(x+e)² ≤ N`, `x+e ≥ 0`, `0 ≤ N − (x+e)²`, and `N − (x+e)² < V0`.

**Coq** (the `(…)%R` means "read the symbols inside as real-number arithmetic"):
```coq
From Stdlib Require Import Reals Lra Psatz ZArith Lia.

Goal forall (N V0 e x : R), (N >= (0)%R)%R -> (e > (0)%R)%R -> ((x * x)%R <= N)%R -> (x >= (0)%R)%R
  -> (N >= ((x + e)%R * (x + e)%R)%R)%R -> ((N - (x * x)%R)%R = V0)%R
  -> ((N >= (0)%R)%R /\ (e > (0)%R)%R /\ ((((x + e)%R * (x + e)%R)%R <= N)%R /\ ... ))).
Proof.
  intros.
  repeat split.
  all: first [ lia | lra | nia | nra | tauto ].
Qed.
```
`intros` brings the assumptions into scope; `repeat split` breaks the big "and" into separate goals; then each goal is handed to a list of arithmetic **tactics** (small proof-finding programs): `lia`/`lra` do *linear* arithmetic over integers/reals, `nia`/`nra` add *non-linear* reasoning (products), `tauto` handles plain logic. The first one that works wins, and Coq's kernel then re-checks what it built.

**Lean:**
```lean
theorem obl (N V0 e x : ℝ) (h0 : N ≥ 0) (h1 : e > 0) (h2 : x * x ≤ N) (h3 : x ≥ 0)
    (h4 : N ≥ (x + e) * (x + e)) (h5 : N - x * x = V0) :
    N ≥ 0 ∧ e > 0 ∧ (x + e) * (x + e) ≤ N ∧ x + e ≥ 0 ∧ 0 ≤ N - (x + e) * (x + e) ∧ N - (x + e) * (x + e) < V0 := by
  refine ⟨?_, ?_, ?_, ?_, ?_, ?_⟩
  all_goals first | omega | linarith | nlinarith | positivity | grind
```
Same idea, different syntax: each assumption is a named hypothesis `h0…h5`, the "and" is split into six goals, and a list of tactics is tried (`omega` for integers, `linarith`/`nlinarith` for linear/non-linear real arithmetic, and `grind`, an SMT-style engine that also instantiates quantified facts and reasons about array reads; whatever it builds is still checked by Lean's kernel).

**Truth values.** A Boolean variable (`Frame: t:bool`) is printed as a proposition variable `(t : Prop)`; `t = true` becomes `t`, `t = false` becomes `¬ t`, and an assignment `t := C` substitutes the proposition `C` for `t`. That is exactly what the obligation means, and it is what lets the bool-valued HumanEval problems be certified (`tests/test_backend_bool.py`).

## 4. How it is wired in

| Piece | File | What it does |
|---|---|---|
| Translate to Coq | `FormalLLM/lspec/coq_translator.py` | prints an obligation as a Coq goal; integers → `Z`, floats → `R`, with casts pushed to the leaves |
| Translate to Lean | `FormalLLM/lspec/lean_translator.py` | same for Lean (`ℤ`, `ℝ`) |
| Run Coq | `FormalLLM/verification/backends/coq_backend.py` | writes a `.v` file, runs `coqc`, caches by hash |
| Run Lean | `FormalLLM/verification/backends/lean_backend.py` | writes a `.lean` file, runs `lake env lean` |
| Z3 decides, Coq/Lean certify | `FormalLLM/verification/backends/cross.py` | the combination used as an engine backend |
| Certify a *finished* derivation | `FormalLLM/verification/certify.py` | replays each accepted step and asks the kernels to check its obligations; Lean gets them **all at once** (`verify_many`: one Mathlib load for the whole derivation instead of one per obligation) |
| Never leak a prover | `FormalLLM/verification/backends/process.py` | a timed-out `coqc`/`lean` is killed **with its children** (see §8) |
| One command, start to finish | `main.py` | `python main.py --case C5-sqrt-paper --assist --certify coq lean` |
| Measure the gap | `benchmarks/automation_gap.py` | records every obligation of the known-good derivations and asks each tool |

**Choosing a backend.** Set the environment variable `FORMALLLM_BACKEND` to `z3` (default), `coq`, `lean`, `cross-coq`, `cross-lean`, `z3+lean` or `z3+coq`, or pass `RefinementEngine(backend=…)` (the command line has `--backend`). `cross-*` means "Z3 decides and supplies counterexamples; a proved obligation is then certified". `z3+lean` means "Z3 decides; **only if Z3 says unknown**, Lean is asked to prove it, and a proof it finds is accepted, kernel-checked": a true step that Z3 cannot decide (quantifiers, arrays) is no longer lost, and Lean never overrules a Z3 counterexample (`backends/fallback.py`; `tests/test_fallback_backend.py` shows Lean rescuing a quantified step and *not* rescuing a wrong one).

**Certifying a finished run (the efficient way).** The search loop needs speed and counterexamples, so it uses Z3. When a derivation is complete, `reliability.py --certify coq lean` re-checks every obligation of the steps that were actually used, and records `"certified: coq 3/3"`.

Why a post-pass rather than certifying inside the search: Lean takes about 7 s per obligation because it loads Mathlib every time; a search that proves dozens of candidate steps would spend most of its time there, and Lean's failures carry no counterexample to learn from.

## 5. What was measured `[ran]`

`benchmarks/automation_gap.py` replays the repo's hand-written, known-good derivations (the paper's sqrt example, integer division, two counting loops, and others from `tests/test_engine_reachability.py`), records **every proof obligation** they generate, and asks each tool.

| | Z3 | Coq (Rocq 9.1) | Lean 4.34.1 + Mathlib |
|---|---|---|---|
| obligations proved, of 11 | **11** | **11** | **11** |
| time per obligation | ≈ 2 ms | ≈ 0.55 s | ≈ 7.4 s |
| gives a counterexample when false | **yes** | no (reports "unknown") | no (reports "unknown") |
| independent small-kernel check | no | **yes** | **yes** |

Also `[ran]`:
* the paper's sqrt derivation (3 obligations) is certified end to end by both kernels (`tests/test_certify.py`);
* the existing derivations also pass when the *engine itself* runs with `FORMALLLM_BACKEND=coq`, `cross-coq` or `cross-lean`;
* a **false** obligation is reported UNKNOWN by Coq and Lean, never PROVED (tested).

### 5.1 A harder sample: the classic programs and the HumanEval pilot `[ran]`

The 11 obligations above are all arithmetic. Programs that search arrays, or whose specifications quantify ("for every k …"), are different:

| Obligations from… | Z3 | Coq (stdlib tactics) | Coq + CoqHammer's `sauto` | Lean 4 + Mathlib (`grind`) |
|---|---|---|---|---|
| the 4 classic derivations of `classic.py` (Factorial, Exponentiation, Linear Search, Max Element), 21 per calculus | 21 | **9** | 11 | **21** |
| the 4 obligations of `choose_num` (HumanEval/102: quantifier + parity) | 4 | **0** | – | **4** |
| the Boolean-valued problems (HumanEval/157, /138) | all | all | – | all |

How to read it. For arithmetic, all three tools are fine. For **quantified statements and array reads** Lean's `grind` is much stronger out of the box than Coq's standard tactics: Coq's `lia`/`nia` cannot instantiate "for every k" at the right k, nor see that `i = n` makes `fact i` and `fact n` the same. I tried the obvious cheap fixes (introduce variables first; `subst` first): **0 of 24** more. I tried CoqHammer's own `sauto` (the paper's tool, but only its internal part: the external provers Vampire/E/cvc4/Z3 that make `hammer` strong are not installed): **4 of 24 more**, the rest time out at 25 s. So on this machine **Lean is the stronger certifier for quantified goals; Coq certifies the arithmetic ones**. Closing the gap for Coq means writing the instantiation by hand (the translator already knows which terms are array indices) or installing CoqHammer's external provers; neither is done.

Speed: Z3 ≈ 2 ms, Coq ≈ 0.5–0.9 s, Lean ≈ 10 s per obligation **when run alone** — nearly all of it is loading Mathlib. Checking a derivation's obligations in one Lean process (`verify_many`) costs about the same as checking one (`tests/test_lean_batch.py` asserts a batch of four takes less than 2.5× a single check).

One case where **no tool but a person** helps: `sum_to_n` as the closed form `2 * r = n * (n + 1)` with `r := n * (n + 1) / 2`. Z3 gives up (non-linear integers with division: `unknown`, timeout). The statement is true because one of `n` and `n + 1` is even, a fact that needs a lemma, not search. A loop (`s := s + i`, invariant `2 * s = i * (i + 1)`) avoids it, and is what a derivation should find. In the HumanEval pilot `HumanEval/60` therefore carries a loop counter `i` in its frame: without one the closed form is the only program the specification can express, and nothing here can check it. With the counter the loop is proved in 0.3 s (`16`, §5.2).

**Honest limits.**
* **The samples are small** (11 + 21 + 4 obligations). They show where the tools differ; they do not show that either can certify everything Z3 can.
* **Only a fragment is translated:** integers, naturals, reals, Booleans (as propositions), arrays read as functions, quantifiers over integers. Array slices and writes raise a clear `UnsupportedForBackend` instead of being dropped.
* **Three meanings differ slightly between tools**, and the code documents them rather than hiding them: (1) `nat` is genuinely non-negative in Coq/Lean but the Z3 translator treats it as a plain integer; (2) division by zero is a fixed junk value (`0`) in Coq/Lean but unspecified in Z3; (3) integer division rounds down in Coq (`Z.div`) and Lean (`Int.fdiv`), while Z3's rounds Euclidean-style (they agree for positive divisors).
* **A Z3 "proved" is not independently checked.** Z3 can in principle be wrong; that is what the certification step is for. If Coq/Lean cannot certify a Z3-proved obligation, `cross` records it as *uncertified* (a count, not an error) unless `require_certificate=True`.

## 6. What this does *not* yet do (so you are not misled)

1. **CoqHammer is not used.** The paper's pipeline calls four external provers through it. Ours certifies with Coq's and Lean's own arithmetic tactics, which sufficed on every obligation measured so far, but may not on harder ones. Installing CoqHammer (and E/Vampire) would likely need WSL with administrator help; it is the first thing to try if a future obligation resists.
2. **Lean and Coq do not guide the search.** They only certify. Using them to *find* proofs for the model (for example `omega` hints, or `exact?` suggestions) is possible but untested.
3. **The certified statement is the engine's, not the paper's.** What is checked is "the proof obligation our laws generate is valid". That the laws match the paper's laws is a separate question (`12`).

## 7a. Two defects found by using the backends on real runs `[ran]`

Both were invisible in the unit tests and showed up only when many real derivations went through the certifier.

1. **A numeral made a variable an integer.** The translator gives an undeclared name the integer sort when an assumption defines it as an integer expression (that is what makes a loop variant `n - i` work). It also fired for `x = 0`, so in one run's `skip` the real variable `x` became `x : Z` and the goal read `IZR x * IZR x <= N`, out of reach of Coq's real-number tactic `lra`. One derivation in five was therefore "3 of 4 obligations certified". Fix: a bare numeral does not make a name whole (`tests/test_backend_coq.py`), and `subst` was added as a fallback tactic. Re-checking the stored derivation: 4 of 4.
2. **A timed-out Coq search left a worker running forever.** `coqc` hands proof checking to a `rocqworker` process; killing `coqc` on a timeout killed only the parent. After a few experiments six orphaned workers were still using CPU half an hour later (and slowing the machine for everything else). Both backends now kill the **whole process tree** on a timeout (`backends/process.py`, `tests/test_process_tree.py` starts a grandchild and checks that it dies).
