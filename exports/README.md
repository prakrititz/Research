# Formal specifications and verified derivations (exported)

Plain-file copy of the Lean specifications and the hand-written refinement derivations of the FormalLLM project, so they can be read, diffed and reused without running anything. Generated by `python benchmarks/export_dataset.py` from `benchmarks/datasets/lean_specs/` (HumanEval and the classics), the Verina clone, `benchmarks/datasets/lean_oracle*.py` / `verina_oracle.py` (derivations) and `benchmarks/results/`.

## What is in here

| dataset | tasks | with a derivation | certified by the engine | re-verified in a fresh Lean process |
|---|---|---|---|---|
| humaneval | 164 | 159 | 159 | 159 |
| classic | 5 | 5 | 5 | 5 |
| verina | 189 | 177 | 177 | 177 |

Kinds of derivation (what the derivation actually contains):

* **humaneval**: definitional 3, loop 87, restate 69
* **classic**: loop 4, restate 1
* **verina**: loop 65, restate 112

* `loop`: an invariant-based loop (the algorithmic content);
* `restate`: no loop; `term`/`cases`/`bind` steps with helper lemmas. Either the specification is already a decidable check (the term is that check), or it enumerates its own search space (all subsequences, all pairs, ...) and the derivation is the brute-force search over that space plus a lemma that the extremum is a member and a bound. These programs are exponential on purpose and say nothing about an efficient algorithm;
* `definitional`: the specification is itself a recursive definition and the answer is that definition.

## How to read one task

`exports/<dataset>/<task_id>/`:

| file | content |
|---|---|
| `spec.lean` | the specification: helper definitions, `<f>_precond`, `<f>_postcond` |
| `description.md` | the English statement |
| `derivation.md` / `derivation.json` | the derivation: the laws `term`, `cases`, `bind`, `loop` with their conditions, invariants, variants and helper lemmas |
| `program.lean` | the finished Lean file: the program as a subtype value `{ρ // postcond ρ}`, the plain function, `<f>_spec_satisfied` and `#print axioms` |
| `status.json` | kind, laws, helper lemmas, certified, independently verified, tests passed |

## What the guarantee is

A derivation is *certified* when the whole term type-checks in Lean, `#print axioms` lists only `propext`, `Classical.choice` and `Quot.sound`, and the program passes the task's tests. It is *independently verified* when the generated file also compiles in a fresh `lake env lean` process with the dataset's own precondition and postcondition text (`benchmarks/verify_derivations.py`). The specification itself is checked against test data only (`benchmarks/lean_eval.py validate`): it accepts the expected outputs and rejects the wrong ones; that is evidence that it says what the English says, not a proof of it.

## Mutation testing

Each derivation was mutated (a number +1, `<` against `≤`, `+` against `-`, ...; at most 3 mutants each) and given back to the engine: Verina 350 mutants, 96.0% rejected; HumanEval 378 mutants, 97.1% rejected. Every survivor was certified and passed all tests (an equivalent mutant or a boundary the specification allows); none was accepted and failed a test. Raw rows: `benchmarks/results/<dataset>/mutation_feedback.json`.

## Tasks without a derivation

Listed with the reason in each `index.md` (column *note*) and in `status.json`. Verina tasks that do not compile on Lean 4.34.1 are blocked by the Lean version, not by the method.

## Re-running

```
python benchmarks/lean_eval.py oracles --dataset humaneval     # derive and certify
python benchmarks/verify_derivations.py --dataset lean_specs         # re-verify in fresh Lean processes
python benchmarks/export_dataset.py                                  # regenerate this folder
```
